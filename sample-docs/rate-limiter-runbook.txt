Rate Limiter Runbook — Internal Reference

Overview
This service implements a distributed, Redis-based rate limiter using a sliding-window
algorithm. It sits in front of downstream microservices and enforces platform-wide
throttling to protect backend infrastructure from traffic spikes.

How it works
Each incoming request is checked against a Redis-backed counter keyed by client identity
and time window. If the request count within the current window exceeds the configured
threshold, the request is rejected with HTTP 429 (Too Many Requests) instead of being
forwarded downstream.

Load testing results
The limiter was load-tested with k6 to its saturation point. At approximately 950
requests per second, gateway CPU reached 98%, and the limiter correctly shed roughly
40% of excess traffic via HTTP 429 responses, while requests that were accepted
maintained a p95 latency of 420 milliseconds.

Known bottleneck
At saturation, Redis CPU stayed around 84%, meaningfully lower than the gateway's 98%.
This indicates the application/gateway layer is the primary bottleneck, not Redis —
horizontal scaling of the gateway layer is the first lever to pull before considering
Redis cluster changes.

On-call escalation
If the rate limiter itself becomes unavailable, requests should fail open (be allowed
through) rather than fail closed, to avoid a total outage of downstream services during
a limiter failure. This is a deliberate design tradeoff between strict enforcement and
availability.
